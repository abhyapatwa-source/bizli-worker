1. Overview

Bizli Worker is a Cloudflare Worker-based AI assistant platform with a Telegram bot front end, a web chat interface, a memory system, tool usage, a production monitoring dashboard, and a structured admin control plane.

At a high level, the worker is a full application runtime that combines:

  • Telegram webhook processing
  • web chat login and conversational exchange
  • user identity and access control
  • Supabase relational storage
  • Cloudflare KV fast state storage
  • LLM orchestration (primarily Groq) with fallback providers
  • tool execution for weather, search, movies, crypto, currency, and more
  • admin dashboard + stats backend
  • scheduled jobs and product QA tests
The app acts like an AI companion product, not just a chatbot. It includes persona shaping, memory behavior, thoughtful prompts, provider management, and even a monitoring “lab” for system health.

2. Architecture

The architecture is layered and intentionally modular. The application is built around a central runtime pattern:

  • Runtime entry: Cloudflare Worker receives HTTP and webhook traffic.
  • Intent routing: Telegram or web messages are normalized and routed into command/auth/chat systems.
  • Memory layer: user state and recent context are loaded from KV and Supabase.
  • Brain layer: a model receives the user message plus system context.
  • Tool layer: when the model calls tools, the worker executes them.
  • Safety/sanitization layer: outputs are filtered before sending to the user.
  • Storage layer: user messages and assistant output go into storage.

Main responsibilities

  • Authentication and PIN flows
  • Memory recall and persisted chat history
  • LLM provider selection and fallback
  • Long prompts, tool calls, and integrations
  • System monitoring and dashboard
  • Scheduled agents + tests

Primary external dependencies

  • Telegram Bot API
  • Supabase
  • Cloudflare KV
  • Groq
  • Gemini / OpenRouter / Cerebras alternatives
  • TMDB, Open-Meteo, Yahoo Finance, CryptoCompare, Tavily/Serper

3. Runtime and request flow

The worker receives both HTTP requests and scheduled tasks. For live chat, the flow is usually:

  1. Request enters Cloudflare Worker
  2. Route is identified in worker/index.ts
  3. Message is translated into a normalized internal request
  4. Auth, maintenance and access checks are performed
  5. Relevant memory/context is loaded
  6. LLM call is made to the provider
  7. Tool calls are executed if needed
  8. Final response is sanitized and sent to user
  9. Conversation is saved to the relevant storage layer
Telegram Update
  ↓
worker/index.ts
  ↓
processTelegramUpdate()
  ↓
auth / admin / chat routing
  ↓
load user + context + memories
  ↓
callGroq() → maybe executeTool()
  ↓
sanitizePersonaLeaks()
  ↓
reply to Telegram / persist data
The most important architectural pattern here is context assembly before inference. The worker loads a user profile, current chat state, memory retrieval, and system instructions before sending data to the model.

4. Entry point: worker/index.ts

The worker entry file is the operational nucleus of the project.

Purpose

  • handle the main Cloudflare fetch lifecycle
  • serve web pages and API routes
  • accept Telegram webhooks
  • handle admin endpoints
  • handle scheduled jobs
  • invoke the correct internal module depending on the request kind

Route examples

GET /dashboard
GET /admin/stats?key=...
POST /web-chat
POST /telegram
GET /privacy
GET /terms
GET /health
POST /admin/test-chat
GET /admin/run-tests

Telegram processing

In the Telegram path, the worker will often call logic such as:

  • auth flow handlers
  • user command handlers
  • group message handlers
  • admin command handlers
  • maintenance gate checks
  • support handling

The code ensures that when a normal user message is received, it does not immediately assume the message is “just chat.” It checks whether the message is:

  • a command
  • part of auth wizard state
  • admin intent
  • a callback response
  • a group message
This is one of the design strengths of the repo: message routing is purpose-aware, not just “send every message into the brain.”

export interface Env {
  TELEGRAM_BOT_TOKEN: string;
  SUPABASE_URL: string;
  SUPABASE_SERVICE_KEY: string;
  GROQ_API_KEY_1: string; GROQ_API_KEY_2: string; ...
  BIZLI_PERSONA: string;
  BIZLI_MEMORY: KVNamespace;
  ADMIN_CHAT_ID: string;
  ADMIN_PASSWORD: string;
  NASA_API_KEY: string;
  TAVILY_API_KEY: string;
  TMDB_API_KEY: string;
  AI: any;
  OPENROUTER_API_KEY?: string;
  GEMINI_API_KEY?: string;
  CEREBRAS_API_KEY_1?: string;
  ...
}

Why this matters

  • It defines the exact secret structure the worker expects.
  • It makes feature toggling possible by binding only the keys that exist.
  • It is a safe source of truth for provider logic and runtime assumptions.

6. Data layer

Supabase wrapper

worker/db.ts wraps PostgREST calls to Supabase:

export async function db(env: Env, path: string, method = "GET", body?: object)

It:

  • builds a REST URL
  • authenticates with the service key
  • sends JSON payloads when needed
  • returns parsed JSON or null

Typical database usage

Common entities are:

  • users
  • messages
  • memories
  • feedback
  • platform_identities
The DB layer is intentionally thin, which is a good design decision: the rest of the app does not hardcode Supabase APIs everywhere.

7. Memory and session management

worker/memory.ts is where the app manages short-term memory, long-term facts, and conversational state.

KV-based session memory

Cloudflare KV is used for fast state that can be stored cheaply and retrieved quickly.

  • chat history
  • timezone
  • language
  • maintenance flags
  • auth state
  • cooldowns / rate limits
  • admin session state

Long-term memory

Long-term memory is not simply raw chat text. The app also stores structured facts and often generates embeddings for retrieval/search.

  • saveMemory() stores a user fact
  • getRelevantMemories() retrieves relevant memory based on context
  • getUserMemories() gives a user’s saved memory list

Helpful state helpers

setAuthStateHelper(env, chatId, { step, userId, ... })
getAuthStateHelper(env, chatId)
clearAuthState(env, chatId)

These are used for guided login, account recovery, and input waits.

The code strongly distinguishes between short-term conversational memory and persistent user memory. That separation is a product-quality design decision.

8. Brain / LLM orchestration

worker/brain.ts is the AI core of the application.

Main purpose

  • select the active AI model/provider
  • build prompt context
  • track cooldowns and provider health
  • route tool calls
  • sanitize output before user delivery

Provider strategy

The app does not rely on a single model. It supports a fallback chain:

  • Groq
  • Gemini
  • Cerebras
  • OpenRouter
  • Cloudflare AI / other AI endpoints

Cool-down and model health management

The worker tracks:

  • provider status
  • rate limits
  • key cooldown windows
  • active provider health
  • which model is currently healthy for text or vision

Safety layer

The code uses a sanitizer to avoid leaky or malformed responses. Examples include:

  • hacky internal tool call leaks
  • instruction-following artifacts
  • generic filler text
  • persona leakage
sanitizePersonaLeaks(response)

This is not a cosmetic step — it acts as a safety control to keep the product coherent and professional.

Tool-call coordination

When the model wants to call a tool, the workflow is typically:

  1. Model emits function call schema
  2. Worker parses and executes tool
  3. Tool returns structured result
  4. Second model pass turns raw result into a polished answer
This is a high-quality pattern for modern tool-augmented LLM applications.

9. Tools and tool execution

worker/tools.ts defines the tool registry and rate-limit policy.

Purpose

  • register tool schemas
  • block or throttle abuse
  • route tool calls to the right implementation
  • make each tool obey a consistent result format

Examples of tool use

  • weather lookup
  • currency conversion
  • movie info
  • web search
  • search/youtube
  • media generation or sending

Rate limiting

The code keeps per-feature quotas in memory and blocks overuse if a user exceeds their allowance.

checkRateLimit(env, chatId, "image")

It is critical for controlling expensive features like deep searches, image generation, or media fetches.

11. Search and deep research

The app contains a dedicated deep-search path, separate from ordinary chat.

Search model

It uses a search pipeline to do the equivalent of “researching the web for the answer,” then reformatting it into a user-friendly briefing.

  • Search API obtains source data
  • Information is summarized
  • Model writes a structured briefing with bullet points and sources
  • It then appends the search result into the user’s memory/history
composeSearchBriefing(env, query, raw, userId)

Deep search is intentionally treated as a special response style, because the user is requesting a research-grade answer rather than a normal conversational reply.

12. Authentication, onboarding, and recovery

Authentication is a real system, not just a casual login path. It uses a user model with identity code and PIN.

Key concepts

  • identity_code: user code, e.g. BZ-XXXX
  • pin_hash: 4-digit PIN hashed for verification
  • platform_identities: maps Telegram/web account to user

Flow

  1. Start signup
  2. Ask for name
  3. Ask for email / DOB / location
  4. Generate identity and set PIN
  5. Persist user and platform mapping
  6. Set user status to approved or waitlist depending on logic

Recovery

Recovery supports:

  • forgot PIN
  • recover account by Gmail
  • admin approve/recover flow
The project includes lockouts after repeated wrong PIN attempts, which is a strong operational and safety measure.

17. End-to-end message flow

1. User messages Telegram or web chat
2. Worker receives request in /telegram or /web-chat
3. Identity + auth check runs
4. Maintenance mode / admin gating is checked
5. User record is loaded from Supabase (or derived from platform identity)
6. Recent KV history is read
7. Relevant long-term memory is retrieved
8. Context is assembled (timezone, user identity, tool capability, support rules)
9. callGroq() sends prompt to the active provider
10. The model decides whether to use a tool
11. Tools execute if required
12. A second synthesis pass produces polished final output
13. The output is sanitized before sending
14. Response is sent to Telegram or web UI
15. User and assistant text are persisted to DB/KV
16. Memory extraction may run asynchronously in the background

This exact lifecycle is the essence of the product.

18. Security and trust model

Strong points

  • PIN hashing and lockouts
  • admin gating for privileged actions
  • support request routing
  • rate limits on heavy features
  • sanitization of model outputs
  • clear separation of user data and system state

Areas to watch

  • many integration points increase the bug surface
  • tool actions can expand attack surface if unguarded
  • user-defined prompts and external web data need strict shaping
  • large prompt templates can be brittle without disciplined testing

Overall, the system has a thoughtful operational model, especially around model safety and app-level control.

19. Contributing and extending the app

Good extension points

  • Add a new tool to worker/tools.ts and implement helper in worker/apis.ts
  • Add a command to worker/commands.ts
  • Add a memory retrieval rule in worker/memory.ts
  • Change model routing in worker/brain.ts
  • Add a dashboard panel under worker/dashboard/tabs

Development workflow

npm install
npx tsc --noEmit
npm run dev
npm run deploy

If you are extending Bizli, the most important principle is to keep routing, memory, and inference separate. That separation is what makes the codebase easier to reason about.

Conclusion

Bizli Worker is a sophisticated AI companion system designed as a production-grade Cloudflare Worker. It integrates chat, memory, provider orchestration, tools, analytics, and admin monitoring into a coherent runtime. The codebase shows careful attention to user experience, resiliency, safety, and operational health.

The single biggest takeaway is that this is not a simple demo bot. It is a full product architecture: a Telegram and web messaging app backed by AI, external data integrations, memory retrieval, an admin control plane, and continuous reliability testing.
